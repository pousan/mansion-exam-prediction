# 過去問予測ワークフロー(マンション管理士 2026 で実施した手順の一般化)

## 大原則(破らない)
- 数える・集計する・比較する処理は必ずコード。頭の中で数えない。
- 数値・条文・事実は問題ID/条番号を添える。根拠がなければ「要確認」と書く。
- 法令は記憶でなく一次資料(e-Gov、所管省庁、法務省)で確認。取得日を記録する。
- 各フェーズ末で止まり、承認を得てから次へ。削除・外部送信・破壊的操作は事前確認。
- LLM に過去年を予測させない(検証は統計モデルのみ)。LLM の解釈予測は別ファイルで、統計順位を見る前に固定する。
- サブエージェントは Sonnet 以下(トークン節約)。大量作業はコードに寄せる。

## フェーズ
1. **取得・仕分け**: 公式サイトから問題/解答PDFを取得し、ファイル名でなく中身で年度・種別を判定。`仕分け記録.csv` に根拠を残す。テキスト版とスキャン版が混在したらテキスト版を正とする。
2. **論点分類表**: 40〜50論点に統合。各論点に定義・含める例・含めない例。パイロット100肢で3モデルの一致率と混同ペアを見て境界を直し、バージョン固定(v1.0→v1.1、変更履歴を残す)。
3. **構造化・タグ付け**: 問題ID=年度-問番号(2桁)、肢ID=年度-問-肢番号。正誤は設問文の極性+正解から**コードで導出**(曖昧は「要確認」、個数問題・特殊問題は別区分)。タグは Sonnet と Opus の独立2系統+不一致のみ裁定+別モデルの盲検確認+人の5%抽出。一致率・κ・下限(Wilson)を記録。
4. **バックテスト**: 年tの予測は t 未満のみ使用。学習3年以上。手法=ランダム/頻度順/周期。指標=カバー率(その年の肢のうち予測上位Kに入った割合)。**的中率は、毎年ほとんどの論点が出る試験では無効**(ランダムでも0.8台)。結果は「傾向の目安」と表現。
5. **次回予測と事前登録**: 出題基準日(実施要領で確認)時点の施行済み改正を一覧化(条番号は e-Gov で照合、未照合は明記)。統計予測とLLM解釈予測は別CSV。事前登録CSV(上位15論点、K=5/10/15)+SHA-256+JST日時を作り、コミットして注釈付きタグ(`preregistration-2026`)。ファイルは `chmod a-w`。**登録後は編集禁止**。補足は新ファイルで追記する。外部タイムスタンプが要るなら push を提案(実行は許可後)。試験後は照合CSVでカバー率を統計とLLMで比較。
6. **練習問題**: 各肢に「根拠の条・項+原文の一部」を付け、コードで e-Gov 原文との部分一致を検証(不一致なら出力しない)。1問=正しい肢1つも検証。`scripts/make_practice_questions.py` が雛形。

## 落とし穴(実際に起きたこと)
- ページ番号除去の正規表現で全角数字を消さない(ASCII数字のみ)。
- 表を含む問題(会計)はテキスト抽出が崩れる。目視で確認。
- WebFetch の要約はURLや内容を作り話することがある。URLは curl で存在確認、PDFは保存して PyMuPDF で自分で読む。
- e-Gov API v1 の法令IDは v2 の検索で確認(適正化法は 412AC1000000149)。附則は本則と条番号が衝突するので MainProvision と SupplProvision を分けて扱う。
- 原文引用は括弧書きを省くと不一致になる。検証で落ちたら引用を直す(解説や肢を原文に合わせて曲げない)。
- 肢の正誤と解説が食い違う草稿を書きがち。生成後に「正しい肢は1つ」をコードで検査する。
- 法令でない資料(標準管理規約など)は基準日の扱いを「要確認」として別フラグにする。

## 成果物の置き場所(例)
`01_原本/`(PDF・法令データ・法改正資料) / `02_マスターデータ/` / `03_分析/` / `05_予測/` / `06_練習問題/` / `scripts/`。各フェーズでコミット。
